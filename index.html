Proving the Numbers Match

Differential testing as the validation standard for reverse-engineered Excel models

Executive Summary

Many of the world's most consequential macroeconomic models are Excel workbooks. Teal Insights converts these workbooks into modern Python software, increasingly with AI coding agents doing much of the work. That raises the question every stakeholder should ask: how do we know the new software produces the same numbers as the original?

Our answer is differential testing. We run the same inputs through the original Excel workbook and through the new Python software, then compare every output. The acceptance bar is 100 percent agreement, judged by a strict and fully documented numerical standard. Any single mismatch fails the release.

The method has already proven itself in practice. The LIC DSF Scenario Tool, built for the Uganda Ministry of Finance around the IMF and World Bank Low-Income Country Debt Sustainability Framework, has banked 47,481 live-Excel comparisons across 132 scenarios and three workbook variants with zero unexplained divergences. On Q-CRAFT, an IMF climate fiscal tool, a single automated run compared 366,588 outputs and caught a release-blocking code generation defect that no human review had noticed.

Beyond validation, differential testing gives us something rarer: an objective, repeatable way to evaluate AI-generated code. Every time an AI agent extracts, rewrites, or refactors part of a model, the change must pass the differential test before it is accepted. This makes the test suite a foundation for our broader evaluation practice for AI products.

1 The Problem: Trusted Models in a Fragile Medium

Institutions such as the IMF and the World Bank publish their analytical frameworks as Excel workbooks. These workbooks are authoritative: debt sustainability assessments, climate fiscal risk analyses, and lending decisions rest on their outputs. But Excel is a difficult medium for serious software. Workbooks are hard to version, hard to test, hard to automate, and hard to integrate with modern data infrastructure. A single workbook can contain tens of thousands of interdependent formulas that no one can inspect at once.

Reverse-engineering these workbooks into Python libraries solves those problems. The logic becomes readable, testable, automatable, and usable at scale: an analyst can run thousands of scenarios in seconds instead of editing cells by hand.

But the rewrite creates a new risk that is worse than the problems it solves. A Python library that almost reproduces the official model is more dangerous than no library at all, because its outputs look authoritative while quietly diverging from the source. Manual spot-checking cannot close this gap. Checking a handful of outputs by hand proves nothing about the thousands of formula pathways that were not checked.

The risk is amplified by how the conversion is done. AI coding agents now perform much of the extraction, code generation, and refactoring. This is what makes the work economical at scale, but AI-written code cannot be trusted on inspection alone. We need correctness evidence that is objective, exhaustive, and cheap to regenerate every time the code changes.

2 What Differential Testing Is

Differential testing is a long-established software validation technique (McKeeman, 1998). The idea is simple: feed identical inputs to two independent implementations of the same specification and compare their outputs. If they disagree, one of them has a bug, and the disagreement tells you exactly where to look.

In our setting the two implementations are called oracles:

  • The Golden Master oracle is the original Excel workbook, the reference implementation. We drive it live through Microsoft Excel itself (via COM automation), so the numbers we compare against are the numbers the institution's own tool produces.
  • The MVP oracle (the system under test) is the reverse-engineered Python library, which computes entirely from its own logic and never touches the Excel file at runtime.

The workbook is its own specification. We do not need to write down what "correct" means for every one of thousands of formulas. We only need to ask the original, and hold the new implementation to its answers.

3 How Teal Insights Applies It: The Design

A comparison is only as trustworthy as the rules behind it. Our standard fixes those rules so that every parity result means the same thing across every tool we build. Six rules do the work:

Identical inputs, enforced.

The test runner prepares each input set once and delivers it to both oracles, which run in isolated processes. Before anything is compared, a pre-flight check confirms both sides can actually receive the same inputs; if they cannot, the run stops with a configuration error instead of producing misleading results.

Two validation layers.

The extracted computation graph is tested first (is the extraction faithful?), then the exported library through its public interface only, exactly as a user would call it (is the artifact we ship faithful?). When one layer passes and the other fails, the defect is localized immediately.

A precise definition of "equal."

Excel and Python legitimately differ in the last binary digits of a number, so exact equality is the wrong test. A comparison passes when the absolute difference is at most 10−6 or the relative difference is at most 10−12 (agreement to 12 significant digits). Both thresholds were calibrated from evidence and are recorded in the standard; in practice, roughly 95 percent of passing comparisons agree bit for bit.

Every output counts.

Error codes must match by class (a #DIV/0! against a #N/A fails), blanks must match blanks, and both sides failing identically is flagged rather than counted as a pass. A crash is recorded as a failure without aborting the rest of the run.

Coverage is designed, not accidental.

Scenarios span the model's headline configurations, single-parameter variations, all combinations of categorical settings, time boundaries, and deliberate error inputs, because divergences cluster at the edges of the input space.

The result is evidence, not a green light.

Every run writes a parity report: one row per comparison, aggregate statistics, the computing environment, a cryptographic hash of the workbook, and, on failure, the exact first diverging cell. The 100 percent bar is enforced by the process exit code, and reports are versioned and refreshed whenever the model or the scenarios change.

4 Why This Fits AI-Assisted Reverse-Engineering

Differential testing is valuable for any reimplementation. For an AI-driven one, it is close to indispensable, for four reasons.

It converts trust in the process into proof about the product.

With AI agents writing extraction code, generating a public interface, and refactoring internals into readable functions, no human reads every generated line. The differential test does not care who or what wrote the code. It measures the only thing that ultimately matters: does the output match the authoritative source?

It is a gate inside the AI loop, not just a check at the end.

Our pipeline treats AI output as a draft. Each incremental AI rewriting pass is bounded to a small piece of the model and must pass the differential test before it is accepted; a failing pass is retried or rolled back. In the rehearsal project this gate repeatedly caught bad AI refactors of model internals, and diagnosis showed most root causes were in the context we gave the agent, which we then fixed. The gate is what makes aggressive, large-scale AI refactoring safe.

It scales where human review cannot.

The Q-CRAFT run compared 366,588 output values against live Excel, covering every public function of the generated library across 68 scenarios. No review process staffed by humans approaches that coverage, at any budget, let alone on every change.

It finds what inspection misses, and says where to look.

The clearest example comes from Q-CRAFT. The generated code looked plausible and the library ran cleanly, yet duplicate function names had silently cut 32 of 51 output series off from users. The differential run caught it and traced every failure to a named root cause.

One Q-CRAFT run, by the numbers

366,588 outputs compared  →  186,672 failures  →  2 root causes:

  • One release-blocking code-generation defect: 186,456 failures, 99.88 percent of the total.
  • One tolerance gap at extreme magnitudes: the remaining 216, of which 175 were rounding artifacts and 41 were genuine divergences at a single extreme input.

5 Differential Testing as Product Evaluation for AI Systems

There is a second way to read everything above. A differential test suite is an evaluation harness for an AI product: a fixed task, a defined input distribution, a trusted reference answer, and a single objective metric (the parity pass rate) that is deterministic, reproducible, and immune to grading disputes. In the language of LLM product evaluation, the Excel workbook is a perfect ground-truth labeler for the code our AI pipeline produces, and every pipeline change can be scored against it.

This framing also marks the method's boundary honestly. Differential testing evaluates computational fidelity and nothing else. Whether the generated interface is ergonomic for economists, whether the documentation is accurate and helpful, whether the underlying model is economically sound: these require human review and complementary evaluation methods, including LLM-assisted ones. In our evaluation stack, differential testing is the deterministic foundation those other evaluations build on.

6 What a Passing Result Does and Does Not Prove

We document the limits of a green result as carefully as the result itself, and each known limit has a designed mitigation.

LimitDesigned mitigation
Parity holds only over the scenarios tested. A perfect score on well-behaved inputs proves agreement on well-behaved inputs. The mandatory coverage design of Section 3, including error and boundary scenarios, and stating coverage explicitly rather than implying completeness.
Matched failures prove nothing. Two oracles producing the same error exercised no computation. Matched errors fail the run unless a scenario explicitly declares that it tests an error path.
Evidence can go stale. A report is only meaningful for the exact workbook and configuration that produced it. Workbook content hashes in the report, hard failure on mismatch, and refreshing committed reports on every relevant change.
Fidelity is not validity. Differential testing proves the Python library reproduces the workbook, not that the workbook itself is economically correct. Shared assumptions in test preparation are kept to a minimum; model validity remains the domain of the issuing institution and of expert review.

We regard this candor as a feature of the method. Knowing precisely what a test proves is what makes the proof usable.

7 Where It Is Used Today

Differential testing governs all of Teal Insights' Excel reverse-engineering work:

  • LIC DSF Scenario Tool (licdsf-scenario-tool): an open-source scenario-analysis tool for the IMF and World Bank Low-Income Country Debt Sustainability Framework, built for the Uganda Ministry of Finance. Every number the tool presents is verified against the official template. The banked evidence covers 132 scenarios plus the baseline across three workbook variants: 47,481 live-Excel comparisons with zero unexplained divergences, restore-path integrity confirmed after every mutation cycle, and a generated parity report that ships with the tool so a skeptic can rerun the evidence.
  • py-lic-dsf (py-lic-dsf): the standalone Python library track for the LIC DSF itself, reproducing the template's stress-test indicator outputs under the same golden-master validation standard.
  • py-q-craft (py-q-craft): the Python library generated from the IMF's Quantitative Climate Risk Assessment Fiscal Tool (Batini et al., 2024), with more than one hundred country datasets. Its full differential run compares 366,588 outputs across every public function of the library, and has already caught and localized release-blocking defects.
  • py-tiny-dsa (py-tiny-dsa): the standalone Python library generated from Tiny DSA, a compact debt sustainability model built deliberately to exercise Excel's most hazardous patterns (dynamic references, cross-sheet lookups, time recursion). It passed all 1,770 output comparisons against live Excel, with the underlying arithmetic agreeing bit for bit.

8 Conclusion

Reverse-engineering an institutional Excel model is only worth doing if the result can be trusted, and trust must be earned by evidence rather than asserted. Differential testing supplies that evidence: the original workbook serves as its own specification, every output of the new software is held to it under a strict and documented standard, and the whole examination is automated, so it runs on every change rather than once. For AI-assisted engineering the method does double duty, serving both as the release gate that makes large-scale AI code generation safe and as the deterministic core of our evaluation practice. It is how a Python library earns the right to stand in for the official model.
